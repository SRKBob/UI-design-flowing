# SPEC 六节真实模板

复制下面整块，填空。写成 `SPEC.md` 放项目根，后续每一步先读它。

---

```markdown
# SPEC — <项目名>

## PROBLEM 问题是什么
<谁> 在 <什么场景> 下遇到 <什么麻烦>。带具体的人、具体的动作、具体的量。
例：运营要看数，但不会写 SQL，每次都得等人跑。

## SOLUTION 打算怎么解决
一句话讲清产品主张。
例：一个能直接问、直接看的数据台。

## USER STORIES 用户故事
这一节最长。一条一句，逐条列。
- 作为 <角色>，我想 <动作>，这样 <好处>。
- 例：作为运营，我想直接问一句话拿到数，这样我就不用等人。
（这一版预计 N 条）

## IMPLEMENTATION 实现上的决定
- 页面清单与类型：<落地页 / 控制台 / 工作台 / 移动端 …>，每页一句话说明
- 技术栈：<...>
- 边界：<不接什么、不依赖什么>

## TESTING 怎么测
只测**外部行为**，不测实现细节。
- <用户能观察到的行为 1>
- <行为 2>

## OUT OF SCOPE 这一版不做
- <明确排除的功能 1>（为什么：<...>）
- <排除 2>
```

---

## 填写要点

| 节 | 容易写坏的地方 | 正确做法 |
|---|---|---|
| PROBLEM | 写成"要做一个 dashboard"这种方案，不是问题 | 写**人和麻烦**，不写解法 |
| SOLUTION | 塞进一堆功能 | 一句话，能被复述 |
| USER STORIES | 只写两三条，或写成功能清单 | 写到"每条都能验"为止；每条都有角色/动作/好处 |
| IMPLEMENTATION | 把页面细节写成设计稿 | 只写**有几个页面、什么栈、边界在哪**；视觉细节留给 ② 定方向 |
| TESTING | 写单元测试怎么mock | 只写外部可观察行为 |
| OUT OF SCOPE | 空着 | 必须写——它是防止改到第三次才发现跑偏的那道闸 |

## 一条真实示例（可直接照抄结构）

```markdown
# SPEC — 运营数据台

## PROBLEM
运营要看数，但不会写 SQL，每次都得等人跑，一问一等就是半天。

## SOLUTION
一个能直接问、直接看的数据台。

## USER STORIES
- 作为运营，我想直接问一句话拿到数，这样我就不用等人。
- 作为运营，我想把常看的几个指标固定在首页，这样我不用每次重新找。
（共 12 条）

## IMPLEMENTATION
- 四个页面：落地页 · 控制台 · 工作台 · 移动端
- 技术栈：<待确认>

## TESTING
- 问一句能拿到数，错误问法有明确提示
- 首页固定的指标刷新后还在

## OUT OF SCOPE
- 不做团队协作（这一版只服务个人使用）
- 不做自定义看板（等基础页面跑顺再说）
```
