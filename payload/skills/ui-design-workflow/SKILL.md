# UI 设计工作流

四个角色在同一个项目里**接力**，不是四件互不相干的事：

```
① 需求分析 SPEC  →  ② 前置 Skill ROUTE  →  ③ 生成页面 BUILD  →  ④ 代码理解 GRAPH
   把话变成规范        这一页按谁的规矩        到这才开始写代码        关系图建起来
```

一条主线：**不是让 AI 更努力，是让它在正确的时间做正确的事。** 中间真正写代码的那一段，只需要专心写代码。

三条铁律：

1. **没走完 ①②，不许写 UI 代码。** 用户催也要先说一句"我先把方向定下来"。
2. **定过的东西必须落盘。** SPEC、路由结论、设计系统都写进项目里的文件，后面每一步先读它。方向漂移是这类任务最常见的翻车方式。
3. **一次只当一班的岗。** 做这一段的角色就做这一段，不要顺手把下一段的活干了（尤其别在"定方向"时就开始写组件）。

## ① 需求分析 · SPEC：把话变成规范

**先自己查，再问人。** 上手先读项目现有的代码、README、`PRODUCT.md`、`DESIGN.md`、设计稿、需求单——能自己查到的绝不问。

**只拦真正的关键信息，且一次问完。** 目的是把用户"随口说的那句话"补成一份能照着做的规范，不是走问卷。一次把缺口问清，别挤牙膏式追问。

**用户说得越清楚，这份规范就越准。** 所以开工时明说一句"你多说两句，我就会写得准一些"，把输入成本前置，而不是反复返工。

产出：`SPEC.md` 放在项目根，六节（模板见 `references/spec-template.md`）：

| 节 | 写什么 |
|---|---|
| PROBLEM 问题是什么 | 谁在什么场景下遇到什么麻烦，要有具体的人和数据 |
| SOLUTION 打算怎么解决 | 一句话能讲清的产品主张 |
| USER STORIES 用户故事 | 最长的一节，"作为 X，我想 Y，这样 Z" |
| IMPLEMENTATION 实现上的决定 | 有哪几个页面、什么技术栈、边界在哪 |
| TESTING 怎么测 | **只测外部行为，不测实现细节** |
| OUT OF SCOPE 这一版不做 | 明确排除什么，避免范围蔓延 |

规范里**不能编**：缺的部分标「待确认」，不要替用户发明目标用户、卖点或数据。

> 为什么值得花时间：**真正浪费时间的，是改到第三次才发现方向错了。**

## ② 前置 Skill · ROUTE：这一页按谁的规矩

**不同的页面该有不同的规矩——不是规范越多越好。** 同一个项目里，落地页、控制台、工作台、移动端各守各的规范；用错地方的规范，比没有规范更糟（把落地页那套"大留白 + 巨型标题"套到控制台上，一屏放不下几个数据，标题还会压住数字）。

做法：

1. 从 SPEC 的 IMPLEMENTATION 节读出有哪几个页面，**给每个页面判类型**：落地页 / 控制台或仪表盘 / 工作台或工具 / 移动端 / 文档。一个项目里四种都有也正常。
2. 查 `references/routing-matrix.md` 找到该类型对应的规范要点（样张、密度、字体、该避免什么）。
3. 需要成体系的风格与配色时调 **`ui-ux-pro-max`**：按产品类型查表，产出配色、字体、版式骨架、**该避开的反模式**、交付前检查项。
4. 用户给了参照站、或说"像 X 那样"时调 **`taste`**：扒下那个站的设计 DNA（tokens + 为什么），并与本页规范合并（冲突以用户明确指定的参照物为先）。
5. 项目里已有成熟的视觉体系时调 **`interface-design`**：确认 depth 策略、间距基数、按钮高度等，写进它认的 `.interface-design/system.md`。

产出：`design-system/<项目slug>/MASTER.md`（全局：颜色/字体/间距/圆角/组件规则）+ `pages/<页面>.md`（只写该页与 MASTER 不同的地方，**页面文件优先于 MASTER**）。

产物归属只有一套，别让三份文件争同一件事：

| 文件 | 谁写 | 冲突时 |
|---|---|---|
| `SPEC.md` | ① | 最高，视觉偏好不能推翻"产品是什么" |
| `design-system/<slug>/MASTER.md` | ②（ui-ux-pro-max 产出） | 高 |
| `design-system/<slug>/pages/<页面>.md` | ②（页面级偏离） | **高于 MASTER** |
| `.interface-design/system.md` | ②（interface-design 产出） | 与 MASTER 同级，取更新的那份并在报告里点出冲突 |
| `PRODUCT.md` / `DESIGN.md` | `impeccable` 的既有约定 | 采纳，分别放产品真相与视觉真相 |

## ③ 生成页面 · BUILD：到这才开始写代码

- 每做一个区块前回读 `MASTER.md`；本页有 `pages/<页面>.md` 就以它为准。
- 用真实内容，不要 Lorem ipsum 凑数；没有的图用明确占位并说明。
- 状态要齐：hover / focus / disabled / loading / empty / error。**空状态和错误态最常被漏。**
- 可访问性底线：正文对比度 ≥ 4.5:1、键盘焦点可见、点击区域够大、图片有替代文本、尊重 `prefers-reduced-motion`。
- 响应式至少看 375 / 768 / 1024 / 1440。
- 想加花哨效果时先回答"它服务 SPEC 的哪一条"，答不上来就别加。
- 需求是"做得高级/别模板脸"时调 **`impeccable`**，按它的模式（Persuade / Operate / Read / Experience）与工艺底线做。

## ④ 代码理解 · GRAPH：关系图建起来

页面能跑不等于项目能长大。这一步把"这个项目长什么样"写成可交给下一个人的东西，之后每次改都先读它。

产出 `ARCHITECTURE.md`（或并入现有 `DESIGN.md`）：目录与模块职责、页面 → 组件 → 数据流的关系、共享 token 与复用组件清单、已知的技术债与边界。工具无关，纯文本 + Mermaid 可选；需要出图时用 **`archify`**。

另做一轮**交付检查**（这是它该有的位置——先看懂全貌，再挑毛病）：

1. **机械层**：跑 `impeccable` 的检测器扫源文件或线上 URL（59 条确定性规则，覆盖 AI 味反模式与通用质量问题）。有 primary findings 时它会返回退出码 2——那是信号不是失败。
2. **判断层**：用 `impeccable` 的审查/打磨通道对照 ② 定的规范逐条过。
3. 输出**可执行的修改清单**（改哪 / 改成什么 / 为什么），不要只给"再精致一点"。改完最多再确认一轮就收尾。

## 路由表：什么时候用哪个技能

| 面对的情况 | 用这个 |
|---|---|
| ① 把模糊需求固化成可执行规范 | 本 skill 的 `references/spec-template.md` |
| ② 判断这一页该守哪套规矩 | 本 skill 的 `references/routing-matrix.md` |
| ② 要成体系的风格 / 配色 / 反模式清单 | `ui-ux-pro-max` |
| ② 用户给了参照站，或说"像 X 那样" | `taste` |
| ② 沿用或建立既有产品的视觉一致性 | `interface-design` |
| ③ 要做得高级、有品位、去 AI 味 | `impeccable` |
| ④ 画架构/流程图 | `archify` |
| ④ 交付前挑毛病 | `impeccable` 检测器 + 审查通道 |

**不要为了"都用上"而全调一遍**——用不上的技能只会稀释注意力。

## 常见翻车与对策

| 症状 | 真实原因 | 对策 |
|---|---|---|
| 页面能跑但很模板脸 | 跳过 ②，凭模型默认审美硬写 | 回 ② 查表定方向，尤其把"要避开的反模式"写下来 |
| 控制台做得像官网、一屏放不下几个数 | **规范用错了地方** | 回 ② 重新判页面类型，换成产品规范（信息密度、栅格） |
| 改着改着风格散了 | 方向没落盘，每轮重新发挥 | 方向写进 `MASTER.md`，每轮先读 |
| 改到第三次才发现方向错 | ① 没落成文档，没人当真 | 补 `SPEC.md`，让 OUT OF SCOPE 也白纸黑字 |
| 越改越花、越改越乱 | ③ 里乱加效果 | 每个效果都要能回答"它服务 SPEC 的哪一条" |
| 审查报告看得爽但没改 | 只出结论不出清单 | 审查必须给"改哪/改成什么/为什么" |
| 页面在手机上崩 | 只看了桌面断点 | 375 / 768 / 1024 / 1440 都看 |

## 工具差异

本工作流**不依赖任何 AI 工具私有的命令**，四个技能在细节上会引用具体能力（浏览器截图、子 agent、斜杠命令）。各工具的能力矩阵与降级路径见 `references/capabilities.md`。
